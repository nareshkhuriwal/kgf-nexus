# Nexus as the KGF.Nexus service of KGF Cloud

**Status:** design proposal, recorded as
[ADR-0033](adr/0033-nexus-as-kgf-nexus-service.md) (*Proposed — pending owner
sign-off*). It was written on 2026-09-26 against Nexus `main` at `82b9ec8`
and a **read-only** reading of the KGF Cloud repository
(`/Users/nareshkhuriwal/Khuriwalgroup/kgf-cloud`, working tree as found that
day). Paths starting `kgf-cloud:` refer to that repository. Nothing has been
deployed, and nothing in kgf-cloud has changed.

**Updated at the wave-3 integration (2026-09-26).** Nexus's side of steps 1-3
of the merge plan (§13) now exists on the integration branch: KGF-context
authentication and the tenancy mapping (ADR-0024, OPERATIONS §24), per-service
database logins (F115, OPERATIONS §20.12) and the KGF-compatible audit export
(ADR-0025, OPERATIONS §25.2). Two owner decisions are recorded here:

- **(a) Engine features stay; cost management goes to KGF billing.** Quota
  enforcement, usage metering and its export, and the KGF-compatible audit
  export are kept in Nexus. The cost-management branch (price books, budgets,
  cost UI; `feat/cost-management`, ADR-0023, findings F134-F135) is held out
  of Nexus: rating and budgets belong to kgf-billing (§9.1, §11).
- **(b) One Nexus namespace per KGF resource group**, i.e. per (organization,
  subscription, resource group), as ADR-0024 implements. This replaces the
  per-subscription proposal this document first made; the reasoning is in §6.

Nexus is **not a separate hosted product**. It ships as one service of KGF
Cloud, in the `KGF.Nexus` provider namespace. KGF Cloud owns everything around
the engine:

- the gateway and the signed request context;
- identity;
- the tenant directory: organizations, subscriptions, resource groups and quotas;
- billing, policy, the provider registry and the portal;
- audit export.

Nexus provides the workflow engine and the worker agents. Neither Nexus nor
KGF Cloud is production-ready. Both repositories say so. Every decision marked
**OPEN-n** belongs to the owner and is collected in
[§14](#14-open-decisions-for-the-owner).

## 1. What exists today on each side

**KGF Cloud** (kgf-cloud: README.md, docs/platform-services.md, docs/adrs/0005):

- `services/nexus` was generated by `tools/new_service.py`. It is a
  **simulation**, and it says so in every layer:
  - the manifest declares `executionModes: ["simulation"]` and
    `catalog.state: "simulation"`;
  - every row carries `simulation boolean CHECK (simulation)`
    (`services/nexus/migrations/001_nexus.sql`);
  - the run workflow sleeps 2–5 s and records "Simulated run: no data was read
    or written." (`internal/app/workflow.go`).
- It serves ARM-shaped routes:
  - `PUT|GET|DELETE …/providers/KGF.Nexus/pipelines/{name}`;
  - `POST …/pipelines/{name}/run`;
  - `GET …/pipelines/{name}/runs[/{runId}]`.

  The pipeline create schema is a small Data-Factory-like model:
  `source{kind,ref}`, `sink{kind,ref}`, `schedule` and `transforms[]`
  (`api/schemas/pipeline.create.json`).
- It runs its own Temporal worker on queue `kgf-nexus-v1`, with an outbox
  dispatcher, for **one** organization (`KGF_ORGANIZATION_ID`,
  `cmd/kgf-nexus/main.go:108`).
- ADR-0005 (Accepted, 2026-09-16) names `KGF.Nexus` as a provider namespace. Its
  validation includes a smoke test that creates, runs and deletes a simulated
  Nexus pipeline through the gateway. `smoke-aks.yml` also asserts that the run
  came back `simulation: true` (kgf-cloud: docs/platform-kubernetes.md:50).

**Nexus** (this repository):

- A workflow engine with six control-plane services on one PostgreSQL schema
  (ADR-0011): gateway, workflow manager, DAG engine, scheduler, resource
  manager, event service.
- Pull-based Go worker agents (ADR-0005), a result store (ADR-0008), an
  optional NATS outbox relay (ADR-0003), and a React console.
- Its own authentication (sessions, API keys, scoped tokens), tenancy
  (MULTITENANCY.md), quotas and a usage ledger (ADR-0021), and an audit log.
- Since the wave-3 integration: `X-KGF-Context` authentication with the
  KGF-to-Nexus tenancy and role mapping (ADR-0024; the earlier SSO draft of
  that ADR was withdrawn and reverted), and a hash-chained audit trail with a
  KGF-shaped export and sinks (ADR-0025). Cost management (ADR-0023) is held
  out and moves to kgf-billing ([ROADMAP.md](ROADMAP.md)).

The merge replaces the simulation with the engine. It also turns off the parts
of Nexus that KGF Cloud already owns (§11).

## 2. Where each component lives

```
 browser ──▶ kgf-gateway ──(X-KGF-Context, aud=kgf-nexus)──▶ kgf-nexus  (KGF.Nexus provider front, kgf-cloud:services/nexus)
                 │                                              │  ARM routes, api-version, pkg/authz, manifest,
                 │ tenantdir / registry / identity              │  conformance; no engine logic
                 │                                              ▼
                 │                               Nexus control plane (this repo), in-cluster only, no public ingress
                 │                               api-gateway · workflow-manager · dag-engine · scheduler ·
                 │                               resource-manager · event-service · artifact-gc
                 │                               PostgreSQL (one database) · NATS (optional) · object store
                 │                                              ▲
                 │                                              │ gRPC/TLS, outbound from the worker, NOT via kgf-gateway
 customer- or KGF-run workers:  nexus-agent (subprocess | docker | kubernetes executors)
```

| Component | Where it runs | Owned by |
|---|---|---|
| **KGF.Nexus provider front** | `kgf-cloud:services/nexus`, rewritten from the simulation. It keeps the KGF service template: `pkg/httpkit`, `pkg/tenantctx`, `pkg/authz`, `pkg/registryclient` and the S-08 conformance test. It translates ARM calls into calls to the Nexus API and holds no workflow state of its own (**OPEN-1**: or collapse it into the Nexus gateway, §5.3). | KGF Cloud repository |
| **Nexus control plane** (six services, artifact GC, cluster controller) | The KGF platform cluster (`kgf-platform` namespace), from this repository's Helm chart or images. Reachable only from `kgf-nexus` and from workers. | Nexus repository |
| **Nexus database** | One PostgreSQL database for the whole engine (§8). | Nexus migrations |
| **Worker agents** | Customer-run (their network, their executors) or KGF-run (KGF compute classes, kgf-cloud: docs/compute-classes.md). They dial the Nexus gateway's gRPC worker listener directly. | Nexus repository |
| **Object store** | Customer bucket or KGF-provided storage. The agent holds the credentials (ADR-0008). Native Azure Blob (workload identity), GCS and keyless S3 are merged (ADR-0027); on AKS the result store is the stamp's Blob container through workload identity. | deployment |
| **Console** | A KGF portal extension (§10). The standalone Nexus console is not deployed. | Nexus repository (source), KGF portal (host) |

**Why workers bypass the KGF gateway.** The KGF gateway proxies HTTP/JSON with
a 1 MiB body limit and a 60 s upstream timeout (kgf-cloud:
services/gateway/README.md). The worker protocol is gRPC over HTTP/2, uses
long polls of up to 60 s plus a grace period, and carries messages of up to
4 MiB (ADR-0014). So the worker listener is published on its own endpoint (for
example `nexus-workers.<region>`). It keeps Nexus worker credentials (§4.3) and
optional mTLS (TLS.md). Workers never receive an `X-KGF-Context`.

## 4. Authentication: `X-KGF-Context`

Nexus's side is implemented (ADR-0024, `internal/kgfctx`, OPERATIONS §24).
This section is the contract, taken from `kgf-cloud:pkg/tenantctx`; the one
Nexus verifier also attributes audit rows (ADR-0025).

### 4.1 The token

- **Format:** a compact JWS. The header is `{"alg":"EdDSA","typ":"JWT","kid":…}`
  and the signature is Ed25519. Tokens over 8,192 bytes are refused.
- **Claims:**
  - `org`, `sub` (subscription), `rg` (resource group);
  - `principal`, `role` (`operator` | `viewer` | `service`), `request_id`;
  - `obo` and `obo_role` on delegated service calls;
  - `iss`, `aud`, `jti`, `iat`, `exp`.
- **Lifetime:** the gateway mints tokens valid for **1 minute**
  (kgf-cloud: services/gateway/internal/api/handler.go). The verifier caps any
  token at `MaxTTL` = 5 minutes and allows `iat` up to 60 s in the future.
- **Audience:** the gateway mints per destination. Nexus must require
  `aud = kgf-nexus` (its registered service name).
  - **Flag:** `tenantctx` still accepts `aud = "*"` even when an audience is
    configured (kgf-cloud: pkg/tenantctx/tenantctx.go:287). The accompanying
    comment says a configured audience refuses `"*"`. The Nexus verifier
    refuses `"*"` unless `NEXUS_KGF_ACCEPT_ANY_AUDIENCE=true` (F137).
- **Replay:** the verifier remembers each `jti` until the token expires. KGF's
  guard is per process. Nexus has several gateway replicas, so it has the same
  limit unless the guard is shared.
- **Keys:** the gateway's public key is published at
  `/.well-known/kgf-context.json`. Additional trusted keys are configured
  through environment variables. Nexus refreshes and caches the key set and
  accepts any currently published `kid`, so keys can rotate without downtime.

### 4.2 Mapping the context to a Nexus principal

| Context | Nexus principal |
|---|---|
| `role=operator` | KGF's built-in Contributor action set, mapped onto Nexus permissions (ADR-0024 §4), limited to the namespace that `org`/`sub`/`rg` map to (§6) |
| `role=viewer` | Reader (`*/read`, `*/list`) in that namespace |
| `role=service` without `obo` | refused unless listed in `NEXUS_KGF_SERVICE_PRINCIPALS` with the role it acts as (ADR-0024 §4) |
| `role=service` with `obo`/`obo_role` | decide against the human in `obo` with `obo_role`, as KGF's S-10 rule requires |
| `request_id` | recorded on every audit row and log line, so a KGF support reference resolves inside Nexus |

**KGF decides; Nexus re-derives the same decision.** `kgf-nexus` calls
`authz.Enforcer.Require(type, verb, …)` for each route, as the S-08 conformance
suite requires. Behind it, the Nexus API does not trust that blindly: it maps
the context's flat role to KGF's built-in action set and every Nexus
permission to one `KGF.Nexus/*` action, denying unmapped permissions (ADR-0024
§4), and it keeps F101's rule that the path namespace must match the
principal. The Nexus RBAC module catalog (ADR-0012) is not exposed to KGF
users.

### 4.3 What keeps Nexus-native credentials

- **Workers.** An agent authenticates with a Nexus worker token (`nxtok_`,
  role `worker`, scope `worker_rpc`, F114) and, optionally, an mTLS client
  certificate. Tokens are minted through the KGF action
  `KGF.Nexus/workerPools/issueToken`, which `kgf-nexus` turns into
  `POST /v1/namespaces/{ns}/tokens`. So a KGF operator issues them, KGF audits
  them, and Nexus stores them hashed with an expiry.
- **Nothing else.** Human sessions, API keys for people, registration, email
  verification and password recovery are switched off in KGF mode (§11).

## 5. Resource IDs and `api-version`

### 5.1 Tenancy key (see §6 for the mapping)

`/subscriptions/{sub}/resourceGroups/{rg}` (with the context's organization)
identifies exactly one namespace `ns`.

### 5.2 Route mapping

Every route requires `api-version=2026-09-01-preview`, and `kgf-nexus` checks
it with `httpkit.RequireAPIVersion`.

| KGF route (under `/subscriptions/{sub}/resourceGroups/{rg}/providers/KGF.Nexus`) | Nexus API |
|---|---|
| `GET pipelines` | `GET /v1/namespaces/{ns}/specs`. The namespace is the resource group's, so no label filter is needed. |
| `PUT pipelines/{name}` | `POST /v1/namespaces/{ns}/specs`. Specs are content-addressed (F124): an identical body returns the existing version. `generation` = the spec version number. |
| `GET pipelines/{name}` | latest `GET …/specs/{name}/versions` + `GET …/specdefs/{id}` |
| `DELETE pipelines/{name}` (If-Match, Idempotency-Key) | `DELETE /v1/namespaces/{ns}/specs/{name}`, only when If-Match equals the current version, otherwise 412 |
| `POST pipelines/{name}/run` (Idempotency-Key) | `POST /v1/namespaces/{ns}/runs` with `spec_name` and the run idempotency key. Replays return the first run. |
| `GET pipelines/{name}/runs[/{runId}]` | `GET …/runs?spec=…` and `GET …/runs/{id}`. `runId` = `run_` + the Nexus run UUID's 32 hex digits, which fits the existing `^run_[0-9a-f]{32}$`. |
| `POST pipelines/{name}/runs/{runId}/cancel\|pause\|resume\|retry` | `POST …/runs/{id}/cancel\|pause\|resume\|retry` |
| `GET …/runs/{runId}/attempts/{attemptId}/logs` | `GET …/attempts/{id}/logs` |
| `schedules`, `schedules/{name}/backfills` | `…/schedules`, `…/backfills` |
| `workerPools` | `…/workers`, `…/capacity`, `…/platform/config` (pools). Tokens through `…/tokens`. |

### 5.3 Conventions

- **Errors.** KGF's shape is `{"error":{"code","message","request_id"}}`
  (kgf-cloud: pkg/httpkit). Nexus's gateway writes its own JSON error
  (`services/api-gateway/rest/wire.go`). `kgf-nexus` re-shapes errors and
  keeps Nexus's error codes.
- **Long-running work.** KGF providers have no generic Operation resource today.
  A run already is one: a 202 response returns the run, and the client polls it.
- **Idempotency.** KGF's `Idempotency-Key` (8–128 characters) maps to Nexus's
  run idempotency. Deletes use If-Match with the generation, as the
  simulation's delete does today.

**OPEN-1: a separate front, or ARM routes in the Nexus gateway?**

- A thin front in `kgf-cloud:services/nexus` keeps KGF conventions in KGF's
  repository, is covered by KGF's conformance tests, and leaves the engine's
  `/v1` API unchanged. It costs one extra network hop.
- Serving ARM routes in the Nexus gateway removes the hop, but puts KGF
  conventions into this repository.

**Recommendation:** the front. Revisit if latency shows up in measurements.

## 6. Tenancy mapping

**Decided (owner, 2026-09-26): one Nexus tenant and namespace per KGF
(organization, subscription, resource group).** ADR-0024 §3 implements it.

| KGF | Nexus today | Mapping |
|---|---|---|
| Organization (`^[a-z][a-z0-9_-]{1,63}$`) | none: a tenant owns exactly one namespace (MULTITENANCY.md) | recorded on the scope row (`kgf_scopes.organization`) for organization-level queries and billing attribution; part of the namespace hash |
| Subscription (UUID; KGF ADR-0005's billing and quota boundary) | none | recorded on the scope row; part of the namespace hash |
| **Resource group** | tenant ↔ namespace, 1:1 | **one Nexus tenant and namespace per resource group** |
| Resource | spec (workflow) | `pipelines/{name}` |

`namespace = "kgf-" + hex(sha256("kgf-nexus/v1" 0x00 org 0x00 sub 0x00 rg))[:32]`
(lower-cased inputs). It is provisioned on the first request for the scope, in
one transaction, as a `tenants` row plus a `kgf_scopes(namespace, tenant_id,
organization, subscription, resource_group)` row (migration 0032); a namespace
that exists but was provisioned for another triple is refused, never adopted.
A context without subscription and resource group is refused
(`403 kgf_scope_required`). `GET /v1/auth/whoami` and `kgf_scopes` give the
readable triple.

**Why per resource group rather than per subscription** (this document first
proposed per subscription):

- **It is KGF's own unit of isolation.** In KGF a resource group is the scope
  that owns resources, lifecycle and role assignments; two resource groups of
  one subscription are routinely different teams or environments (a `dev` and
  a `prod` group). Mapping them to one namespace would share their workflows,
  runs, schedules, secrets, audit chain and worker pools, and make "who can see
  this run" coarser in Nexus than in KGF.
- **Nexus isolates by namespace, and every guarantee follows it.** Tenant
  ownership (migrations 0013-0015), F101's per-object checks, fair share
  (ADR-0017), quotas (ADR-0021), the per-namespace audit chain (ADR-0025),
  agent NATS identities and worker tokens are all per namespace. Per resource
  group, each of them holds at KGF's finest workload scope with no new Nexus
  concept, where per subscription the resource group would be a mere label that
  every list, check and quota would have to honour separately (the label
  filtering this document first proposed, now unnecessary).
- **Deriving, not labelling.** A derived namespace needs no Nexus-side
  onboarding and cannot drift from KGF: deleting and recreating a resource
  group with the same name maps to the same namespace, and the organization is
  inside the hash, so identical subscription and group names in two
  organizations never collide.

**What it costs, and how it is handled:**

- **Quotas.** KGF's quota boundary is the subscription, Nexus's is the
  namespace. A subscription-level `KGF.Nexus` limit must be either divided
  among the subscription's resource groups by the `kgf-nexus` reconciler (each
  namespace gets its locked share), or enforced by KGF at admission while
  Nexus enforces the per-group share. See §7 and OPEN-5.
- **Workers.** An agent serves one namespace (agents[].namespace, F129), so a
  worker pool serves one resource group. Customer-run pools are per group
  anyway; a KGF-run shared pool is one agent deployment per group it serves.
- **Opaque names.** Namespaces are hashes; operators read `kgf_scopes`.
- **Lifecycle.** Tenants are created by traffic; nothing deletes one when KGF
  deletes the resource group (retention follows Nexus's rules; ADR-0024).

Nexus's own registration (`POST /v1/auth/register`) and platform-operator
onboarding are not served in `NEXUS_AUTH_MODE=kgf`. Tenants come into existence
only this way.

## 7. Quotas

- **What KGF has.** `tenantdir.subscriptions.quota_resources` (default 100) is
  the only quota dimension (kgf-cloud: services/tenantdir/migrations/001_hierarchy.sql:16).
  The resource ledger enforces its own project resource limit.
- **What Nexus has.** Exact concurrent quotas in the claim: in-flight attempts,
  CPU, memory, GPU and custom resources. It also enforces run-creation limits
  (`max_active_runs`, `max_runs_per_hour`), with `locked` so that only a
  platform operator can loosen them (ADR-0021).

Proposal:

1. **KGF sets the limits, Nexus enforces them.** tenantdir, or a plan in
   billing (**OPEN-5**), gains a per-subscription document for `KGF.Nexus`
   carrying the ADR-0021 dimensions (and ADR-0032's shared provider rate
   limits). Because each resource group is its own namespace (§6), `kgf-nexus`
   reconciles it into one `PUT /v1/namespaces/{ns}/quotas` with `locked: true`
   **per resource group**, dividing a subscription-wide limit among the groups
   (by default equally, or by a per-group allocation the document carries), as
   a service principal acting as a platform operator. This runs on subscription
   or resource-group change and on a periodic re-sync. A namespace admin can
   then only tighten limits, and in KGF mode no human has that role inside
   Nexus.
2. `quota_resources` can bound the **number of pipelines** in a subscription.
   `kgf-nexus` would enforce it on `PUT pipelines`, because Nexus does not
   count specs.
3. **A missing KGF document means locked, conservative defaults, not
   unlimited.** ADR-0021's "absent means unlimited" suits self-hosting, not a
   shared platform.
4. Quota-blocked attempts stay PENDING with `pending_reason =
   quota_exceeded: …`. The portal shows that reason as it is.
5. Quota enforcement has a cost: a quota-bound namespace's dispatches are
   serialized across scheduler replicas (ADR-0021; laptop figures in
   [BENCHMARKS.md](BENCHMARKS.md#quota-bound-cells)).

## 9. Billing and audit

### 9.1 Billing

- **KGF today** ingests only supplier cost, from Azure Cost Management. It has
  no usage-ingestion API or event. The metering model exists only as a plan
  (kgf-cloud: docs/billing.md; docs/enterprise-platform-plan.md §14).
- **Nexus has** an append-only usage ledger with one row per dispatched
  attempt, written in the same transaction as the attempt's end, and
  deduplicated on `attempt_id`. It exports in two ways (ADR-0021, OPERATIONS
  §21.5):
  - `nexus.usage.recorded.<namespace>` on the Nexus-internal NATS;
  - a pull `Exporter`/`Pump` with a cursor.

Proposal:

1. kgf-billing gains a usage-ingest route, `/internal/usage`, which accepts
   service contexts only and implements the plan's metering event: an immutable
   event id, tenant, resource and operation, meter version, quantity, unit,
   event time and ingest time, with deduplication.
2. A Nexus `metering.Exporter` posts ledger rows with a service context from
   `kgf-nexus-engine`. **Pull, not the bus.** NATS is internal to Nexus and
   optional, and KGF runs no NATS. The cursor makes it restartable.
3. Row mapping:
   - `event_id = ledger_id`, with dedup key `attempt_id`;
   - `organization`, `subscription` and the resource group come from the
     ledger row's namespace through `kgf_scopes` (one namespace per resource
     group, §6);
   - resource = `/subscriptions/{sub}/resourceGroups/{rg}/providers/KGF.Nexus/pipelines/{name}`;
   - meters: `dispatched_attempts`, `reserved_seconds`, `cpu_core_seconds`,
     `memory_gib_seconds` and `gpu_seconds`, plus AI usage units (tokens,
     requests) as custom keys (ADR-0032, merged).
4. What is billed is a KGF product decision (**OPEN-7**). With customer-run
   workers, KGF does not pay for the compute, so resource-seconds serve
   showback. With KGF-run workers, they are chargeable.
5. Nexus's cost management (ADR-0023: price books, budgets, the cost UI;
   `feat/cost-management`) is **held out** by owner decision (a): it is not
   merged, and rating, budgets and cost reporting move to kgf-billing, fed by
   the ledger export above. OPERATIONS §23 records this; findings F134-F135
   are reserved for it.

### 9.2 Audit

- **KGF today:** `audit_events` lives in resource-control (append-only by
  grants) and is exported as CSV by project. There is no emit API for other
  services, no hash chain and no sink (kgf-cloud: docs/audit-export.md).
- **Nexus has (merged, ADR-0025):** `audit_log` for security and
  administrative actions (`quota.update`, `run.retry`, token issue and revoke,
  ...), hash-chained per namespace, fail-closed for security grants, with
  retention and legal hold. Rows record the KGF organization, subscription,
  resource group, principal, on-behalf-of and request id from the context
  kgfctx verified (in KGF mode, the context that authenticated the request).
  `GET /audit/export?format=kgf` and webhook sinks with `format: kgf` emit
  KGF's `audit_events` shape with the chain position alongside
  (OPERATIONS §25.2).

Kept by owner decision (a). KGF still has to define one audit-ingest contract:
either an `/internal/audit` route, or an export pull that the audit exporter
runs against each provider (**OPEN-8**). Until it does, a `kgf`-format sink to
a KGF-side collector, or the export pulled on a schedule, is the delivery path;
once KGF owns ingest the sink is the adapter to it.

## 12. Temporal and the Nexus DAG engine

KGF runs durable lifecycle workflows on Temporal (`pkg/temporalkit`, the
orchestrator, and the simulation's own `kgf-nexus-v1` worker). Nexus has its
own orchestration: a DAG engine, a scheduler, leases, retries and timers, with
PostgreSQL as the source of truth (ADR-0002, ADR-0006, ADR-0010).

**The boundary:**

- **Nexus executes workflow runs.** A pipeline run is never a Temporal
  workflow. Running Nexus runs inside Temporal would mean two schedulers with
  two retry policies, two histories and two definitions of "done" for the same
  work. The simulation's `PipelineRun` workflow and `FinishRun` activity are
  removed.
- **Temporal stays for KGF resource lifecycle**, where it already fits. One
  example is provisioning a KGF-run worker pool: creating compute through a
  KGF execution worker, then registering the agent. Another is a KGF workflow
  that must wait for a Nexus run. It calls `POST …/run` with a stable
  Idempotency-Key and polls the run from an activity. It does not re-run tasks.
- **Delete** of a pipeline is synchronous in Nexus, so it needs no workflow. If
  KGF's resource ledger ever takes over admission for `KGF.Nexus` resources, the
  outbox-to-Temporal pattern from ADR-0002 (kgf-cloud) applies to the
  **definition**, never to runs.
- **At-least-once semantics are unchanged.** Nexus derives idempotency keys,
  distinguishes LOST from FAILED, and fences leases. KGF ADR-0002's
  requirements match: idempotency keys, fencing, and an unknown outcome leading
  to observation.

## 13. Merge plan, service by service

Each step is independently shippable and reversible. The owner carries them out
in order.

0. **Decisions.** Settle the open items of §14. OPEN-4 (tenancy) is decided
   (per resource group); OPEN-6 (RLS) blocks step 3's second half.
1. **Nexus: KGF-mode authentication.** *Done on the integration branch
   (ADR-0024).*
   - The gateway verifies `X-KGF-Context` (§4.1), requiring `aud=kgf-nexus`,
     rejecting `"*"`, applying the jti replay guard and refreshing keys from
     `/.well-known/kgf-context.json`.
   - It maps the context to a principal (§4.2).
   - KGF mode switches off human login, registration and signup (§11).
   - Tests: forged signature, wrong audience, expired token, replay,
     cross-organization and cross-resource-group namespaces, and `obo` decided against the human.
2. **Nexus: the scope mapping.** *Done (ADR-0024 §3, migration 0032):*
   `kgf_scopes(namespace, tenant_id, organization, subscription,
   resource_group)`, provisioned on first use per resource group; no label
   and no internal route needed.
3. **Nexus: database posture for KGF.** Per-service runtime logins are merged
   (F115, OPERATIONS §20.12; strict per-service grants: F132). Then carry out
   the RLS decision (OPEN-6) under its own ADR, with the benchmark from
   [BENCHMARKS.md](BENCHMARKS.md) as the acceptance measurement.
4. **Deploy the engine into the KGF platform cluster.** Use the Nexus Helm
   chart into `kgf-platform` with `kgf_nexus_engine` on the platform
   PostgreSQL server, no public ingress for REST, and a separate worker
   endpoint (§2). Services use per-service signing keys, as KGF's Helm
   already does (`nexus-context-signing-key`).
5. **KGF: rewrite `services/nexus` as the provider front.**
   - Implement the ARM routes of §5 on top of the Nexus API.
   - Keep `pkg/authz` enforcement and extend the S-08 conformance test to
     every new route.
   - Add migration `002` to drop the simulation CHECK, or retire the
     simulation tables.
   - Update the manifest (§3) and the `smoke-aks.yml` assertions.
   - Remove the Temporal worker and the `PipelineRun` workflow.
6. **Quotas** (§7). Add the per-subscription `KGF.Nexus` limits document in
   tenantdir or billing (OPEN-5) and the reconciler in `kgf-nexus`, which
   writes each resource group's share to its namespace. Test with a limit set
   in KGF: an attempt stays PENDING with `quota_exceeded`, and raising the
   limit releases it.
7. **Billing** (§9.1). Add `/internal/usage` in kgf-billing and the Nexus
   exporter. Test: every dispatched attempt appears exactly once after a
   forced exporter restart.
8. **Audit** (§9.2). The Nexus side is merged (ADR-0025: KGF-shaped export
   and sinks); the ingest side waits for KGF's contract (OPEN-8).
9. **Portal extension** (§10). Port the run explorer, DAG, attempts, logs,
   schedules and workers. Remove the Nexus standalone console from the
   KGF deployment.
10. **Acceptance.**
    - KGF's ten release gates (kgf-cloud: docs/kgf-service-delivery.md) and the
      S-08 suite.
    - Cross-tenant negative tests through the gateway (KGF ADR-0001).
    - Nexus's chaos suite against the KGF deployment.
    - A pipeline created, run and observed end to end from the portal.
    - Then set `catalog.state: live`.
11. **Remove the switched-off Nexus features** (§11) from the KGF build, once
    step 10 has held for a release.
