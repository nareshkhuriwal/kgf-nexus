# __WORKFLOW_NAME__

LLM evaluation with a quality gate on Nexus, generated by `nexusctl init llm-eval`.

```
load_dataset --> answer x N (one per batch) --> grade --> compute_metrics --> quality_gate
```

| Task | What it does | Policy |
|---|---|---|
| `load_dataset` | Reads the items (JSONL, or the built-in set) and cuts them into batches | at most `MAX_BATCHES` (64) of at most 50 |
| `answer` | **map** over the batches: the model under test answers every item | retried on `rate_limited`, `transient`, ...; output `max_bytes=65536` |
| `grade` | Three graders per answer: `exact`, `regex`, and `judge` (LLM-as-judge) | memoized 7 days |
| `compute_metrics` | Accuracy per grader and per (grader, category); tokens | |
| `quality_gate` | **Fails the run** if a gated grader's accuracy is below `min_accuracy` | no retry: a failed gate is a verdict |

## The graders

- **exact**: the answer equals the reference after lower-casing, collapsing
  whitespace and dropping trailing punctuation.
- **regex**: the item's `pattern` must match the whole answer; without one,
  the reference must appear as a whole token (`19` matches "It is 19." but not
  `119` or `19.5`).
- **judge**: a judge model (`judge_model`) is given the question, the
  reference and the candidate, under a "You are a strict grader" system prompt,
  and must answer `PASS` or `FAIL`. Use a stronger model than the one under
  test, and spot-check its verdicts against `exact` on data where both apply:
  a judge that passes everything is worse than no judge.

`gate_graders` (default: all three) chooses which graders the gate enforces.
For open-ended answers where exact matching is meaningless, gate on
`["judge"]` alone.

## The mock, and pointing at a real provider

The defaults target the SDK's mock model server (`base_url=http://mock-llm:8089`,
`api_key_env=""`), which answers deterministically. `mock-large` answers the
built-in set correctly and passes; `mock-small` gets about 30% of the
arithmetic wrong and the gate fails the run. That is what the tests check.

```bash
python -m nexus.testing.mock_llm --host 0.0.0.0 --port 8089   # a sidecar named mock-llm
```

For a real provider pass `provider`, `base_url`, `model`, `judge_model`, and the
**name** of the environment variable holding the key as `api_key_env`; deliver
the key as a secret by setting `API_KEY_SECRETS` in `dag.py`, e.g.
`[SecretRef(name="OPENAI_API_KEY", ref="vault://kv/llm/openai")]`. Never pass a
key as a parameter: parameters are stored and shown.

| Provider | `provider` | `base_url` | `api_key_env` |
|---|---|---|---|
| OpenAI (or OpenAI-compatible) | `openai` | `https://api.openai.com` | `OPENAI_API_KEY` |
| Anthropic | `anthropic` | `https://api.anthropic.com` | `ANTHROPIC_API_KEY` |

Calls go through `nexus.llm.LLMClient`: shared rate-limit permits on
`[<provider>, <provider>/<model>]` (configure the namespace's `rate_limits` to
the provider's limits), in-task 429/503 retries, and token usage reported to
the platform's usage ledger as `tokens:<provider>/<model>:input|output` for the
model under test and the judge separately. The tasks need network egress; the
agent's docker executor defaults to `--network none`.

## Input

JSON Lines: `{"id": "...", "prompt": "...", "reference": "..."}`, optionally
`"category"` (metrics are broken down by it), `"pattern"` (for the regex
grader) and `"system"`. Ids must be unique.

## Develop

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt pytest
pytest          # starts the mock in-process: no key, no network, no cost
nexusctl workflow compile dag.py --show
```

## Deploy and run

```bash
docker build -t __WORKFLOW_NAME__:0.1.0 .   # then push, and set IMAGE in dag.py
nexusctl workflow submit dag.py --namespace __NAMESPACE__
nexusctl run create __WORKFLOW_NAME__ --namespace __NAMESPACE__ --wait                         # passes
nexusctl run create __WORKFLOW_NAME__ --namespace __NAMESPACE__ --param model=mock-small --wait  # fails the gate
```
