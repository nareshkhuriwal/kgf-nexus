# __WORKFLOW_NAME__

An eval-gated fine-tuning pipeline on Nexus, generated by `nexusctl init fine-tune`.

```
prepare_data --> validate_data --> submit_job --> wait_for_job --> evaluate --> eval_gate --> register
```

| Task | What it does | Policy |
|---|---|---|
| `prepare_data` | Reads chat examples; splits train / held-out by a hash of the prompt | |
| `validate_data` | Schema, de-duplication, held-out leakage, training-token budget | no retry: a bad export fails the same way twice |
| `submit_job` | Uploads the training file, creates the job | **idempotent** via the effect journal; retried on `rate_limited`, `transient`, ... |
| `wait_for_job` | Polls until the job ends, at most `max_polls` times | heartbeats every poll; checkpoints the poll count |
| `evaluate` | Held-out accuracy of the base model and of the fine-tune | requests a GPU with `--gpu` |
| `eval_gate` | **Fails the run** unless the fine-tune reaches `min_accuracy` and beats the base by `min_improvement` | no retry: a failed gate is a verdict |
| `register` | Writes `registry_dir/<model>.json` with a create-if-absent link | idempotent: a re-run never registers twice |

## Paying for a job once

A fine-tuning job costs money, so a retried `submit_job` must not start a
second one. The task journals each step under the node's idempotency key,
which every attempt of the node shares:

1. if the job was already created, return it;
2. if the file was already uploaded, reuse it; else upload and journal the id;
3. create the job and journal it.

That is the platform effect journal (`ctx.effect_recorded` / `record_effect`),
the weakest of the three idempotency mechanisms: a crash *between* the
provider accepting a request and the journal write can still repeat that one
request. The upload is named, and the job suffixed, with the idempotency key
prefix, so such a duplicate is easy to find and cancel. If your provider takes
an idempotency key on job creation, pass `ctx.idempotency_key` to it instead
and the window closes.

`wait_for_job` checkpoints `{job_id, polls, status}` after every poll: a retry
resumes polling the same job, and `max_polls` bounds the polls across all
attempts, so a job stuck in `queued` cannot hold the run forever.

## Providers

`submit_job` and `wait_for_job` talk to a `FineTuneProvider` (a `Protocol` in
`dag.py`: `upload`, `create_job`, `get_job`), chosen by `provider_kind`:

| `provider_kind` | Implementation |
|---|---|
| `mock-server` (default) | `OpenAICompatibleFineTuneProvider` against the SDK's mock server, which takes uploads as JSON |
| `openai` | The same class with multipart uploads, as `https://api.openai.com` requires |
| `in-memory` | `MockFineTuneProvider`, for unit tests: its state lives in one process |

To use another vendor or a self-hosted trainer, implement the three methods
and add it to `make_provider`.

## GPUs (optional)

Nothing here needs a GPU when the provider trains the model. With
`nexusctl init fine-tune --gpu` (or `USE_GPU = True` in `dag.py`) the
`evaluate` step requests one `GPU_KIND` GPU, for when you serve the held-out
prompts from a self-hosted model on the node (swap `_accuracy` for your
inference code). A self-hosted `FineTuneProvider` that trains on the worker
would give its training task the same `Resources(gpu=...)`.

## The mock, and pointing at a real provider

The defaults (`base_url=http://mock-llm:8089`, `api_key_env=""`,
`base_model=mock-small`) target the SDK's mock model server. Its fine-tuning
endpoints advance a job one status per poll and name the result
`ft:<base>:mock:<job>`; `mock-small` gets about 30% of arithmetic wrong and its
fine-tunes answer correctly, so the built-in data passes the gate. With
`base_model=mock-large` there is nothing to improve and the gate fails.

```bash
python -m nexus.testing.mock_llm --host 0.0.0.0 --port 8089   # a sidecar named mock-llm
```

For OpenAI: `--param provider_kind=openai --param base_url=https://api.openai.com
--param base_model=gpt-4o-mini-2024-07-18 --param api_key_env=OPENAI_API_KEY`,
with the key delivered as a secret by setting `API_KEY_SECRETS` in `dag.py`
(e.g. `[SecretRef(name="OPENAI_API_KEY", ref="vault://kv/llm/openai")]`).
Never pass a key as a parameter. Raise `poll_interval_s` (real jobs take
minutes to hours) and keep `max_polls * poll_interval_s` under
`wait_for_job`'s `schedule_to_close`. The tasks need network egress; the
agent's docker executor defaults to `--network none`.

`evaluate` reports usage for both models under the platform's usage keys; a
fine-tuned id's `:` is mapped to `_` (`tokens:openai/ft_gpt-4o-mini_org__abc:input`).

## Input

JSON Lines of chat examples, `{"messages": [{"role": "user", ...}, {"role":
"assistant", ...}]}` (the last message is the target), or
`{"prompt": ..., "completion": ...}`. The training and held-out sets travel
between tasks inline; for datasets beyond a few MB, write them to object
storage in `prepare_data` and pass references.

## Develop

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt pytest
pytest          # starts the mock in-process: no key, no network, no cost
nexusctl workflow compile dag.py --show
```

## Deploy and run

```bash
docker build -t __WORKFLOW_NAME__:0.1.0 .   # then push, and set IMAGE in dag.py
nexusctl workflow submit dag.py --namespace __NAMESPACE__
nexusctl run create __WORKFLOW_NAME__ --namespace __NAMESPACE__ --param poll_interval_s=1 --wait
```

`registry_dir` is a path inside the task container: mount shared storage there,
or replace `register` with a call to your model registry (keeping it
create-if-absent).
